Core Logic
ESCALATION ENGINE

The heart of ACT.live. Five configurable stages — each with its own trigger day threshold, communication channel, tone, message type, and approval requirement. All parameters are set by the landlord. The agent executes autonomously. Click a stage to inspect it.

Generation Method
Stages 1–2: Template Injection
Variables (tenant name, amount, days) injected into pre-written Dutch templates. No AI API call — fast, cheap, consistent tone.
Generation Method
Stages 3–5: Full AI Generation
Claude claude-sonnet-4-5 generates legally accurate Dutch correspondence. System prompt caches BW article references. Only task-specific fields sent per call.
Human-in-the-loop
Approval Gates at Stage 4–5
High-stakes actions (legal warning, bailiff referral) pause for landlord approval in the Approvals tab before sending. Configurable per landlord account.
Current State
BUILD STATUS

ACT.live follows a structured 10-task MVP plan. Tasks 1–7 are complete and functional. Click any task to inspect what was built and which files are involved.

01
Supabase Schema
Complete
7-table PostgreSQL schema — landlords, tenants, cases, actions, approvals, escalation_configs, properties
Seven relational tables establish the complete data backbone. RLS is disabled on cases, tenants, and actions for MVP speed; it will be re-enabled in Task 9 per-landlord isolation. Key design decision: days_overdue is calculated at runtime in the application layer (not as a GENERATED ALWAYS AS STORED column) because CURRENT_DATE is non-immutable in PostgreSQL and would prevent column creation.
supabase/migrations/001_init.sql
02
Agent Engine
Complete
Core orchestration loop — reads configs, identifies overdue cases, triggers escalation, logs every action
agent.js is the autonomous brain of ACT.live. On each run: connects to Supabase via service role key, reads each landlord's escalation_configs, queries cases where days_overdue exceeds the configured trigger threshold, calls the appropriate prompt or template, logs the resulting action to the actions table, and marks cases for approval if the stage requires it. Designed to run on a cron schedule (Railway Jobs).
src/agent.js src/config.js
03
Claude Prompt System
Complete
Template injection for stages 1–2; full claude-sonnet-4-5 generation for stages 3–5 with BW legal references
prompts.js is the AI bridge. Stages 1–2 use pre-written Dutch templates with variable injection (tenant name, amount, days overdue) — no API cost. Stages 3–5 call claude-sonnet-4-5 with a cached system prompt containing Dutch Burgerlijk Wetboek article references. Per call, only the minimal task-specific payload is sent: tenant first name, amount overdue, days overdue, stage number. No PII beyond what is necessary. Prompt caching applied to system prompt to reduce token cost.
src/prompts.js
04
Email Delivery (Resend)
Complete
CommonJS Resend integration wired into agent.js — confirmed sending Dutch correspondence
mailer.js wraps the Resend SDK in a CommonJS module and is called by agent.js after each action is logged. Emails send successfully and are confirmed via Resend delivery IDs. During testing, Resend's test mode restricts delivery to the account owner's email — tenant emails are overridden to the owner address in development. In production, real tenant emails are used.
src/mailer.js
05
Escalation Settings Frontend
Complete
React UI for landlords to configure per-stage trigger days, tone, message type, approval requirements
Built in React + Vite. Landlords access a settings page where each of the 5 escalation stages can be fully configured: trigger day threshold, communication channel (email/WhatsApp), tone (friendly/firm/formal/legal), message type (template or AI-generated), and whether human approval is required before sending. All settings persist to Supabase escalation_configs table via the anon key. Environment variables: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_LANDLORD_ID.
src/EscalationSettings.jsx .env
06
Cases Dashboard
Complete
Live view of all active cases — tenant info, days overdue, current stage, last action, status
The cases dashboard gives landlords a real-time operational view. Each row shows: tenant name, property address, total amount overdue, days overdue (calculated at runtime), current escalation stage, last action taken (with timestamp), and case status (active/resolved/paused). RLS is disabled for MVP — all cases visible to any authenticated session. Task 9 will scope each landlord to their own cases only via RLS policies.

07
Approvals Tab
Complete
Human review interface for pending high-stage actions before they send
Stage 4 (Legal Warning) and Stage 5 (Bailiff Referral) require landlord approval before ACT.live sends correspondence. The Approvals tab surfaces all pending actions — showing the full AI-generated letter text, the tenant details, and the case context. The landlord can Approve (triggers send) or Reject (logs rejection, pauses case). This human-in-the-loop gate is the core safety mechanism for legally sensitive communications.

// agent.js — core run loop (simplified)
async function runAgent() {
  const cases = await supabase
    .from('cases')
    .select('*, tenants(*), escalation_configs(*)')
    .eq('status', 'active');

  for (const c of cases.data) {
    const daysOverdue = calcDaysOverdue(c.due_date);  // runtime calc
    const stage = getStage(daysOverdue, c.escalation_configs);
    const letter = stage <= 2
      ? injectTemplate(stage, c)                    // no API call
      : await generateWithClaude(stage, c);   // API call — minimal payload
    await logAction(c.id, stage, letter);
    if (!requiresApproval(stage, c.escalation_configs))
      await sendEmail(c.tenants.email, letter);
  }
}
Trust Model
SECURITY ARCHITECTURE

ACT.live handles tenant PII, financial arrears data, and legally significant correspondence. The security model is designed so that the highest-risk data never leaves the Supabase boundary, and AI generation never receives more than the minimum task-specific payload.

🔑
Dual Key Architecture
Frontend uses Supabase anon key — subject to RLS policies. Backend agent uses service role key — bypasses RLS only on the server side. Credentials are never shared across layers.
🛡️
Minimal AI Payload
Claude API receives only: tenant first name, days overdue, amount overdue, stage number. No email addresses, no phone numbers, no case history, no credentials from other tenants.
🔒
Row Level Security (Task 9)
RLS is disabled for MVP speed. Task 9 enables per-landlord RLS policies on cases, tenants, and actions — making cross-landlord data access structurally impossible at the database layer.
📋
Full Audit Trail
Every action — every letter generated, every email sent, every approval decision — is immutably logged in the actions table with timestamps. This log is the legal evidence chain for court proceedings.
✋
Human Approval Gates
Stages 4 and 5 (legal warning and bailiff referral) never send autonomously. The agent writes the draft and pauses. The landlord reviews and explicitly approves before any legal communication is delivered.
🌐
GDPR-by-Design
Tenant PII stays within Supabase — a GDPR-compliant EU-hosted platform. AI generation never accumulates or stores personal data. The security architecture is a selling point, not a liability.

ROADMAP

From demo-ready to production-hardened to market-leading. Three clear phases with defined deliverables.

Phase 1 — Complete
Core Agent — Tasks 1–7
Database schema, autonomous escalation engine, AI prompt system, email delivery, React frontend with cases dashboard, escalation settings, and approvals tab. The product works end-to-end in a single-landlord context.
Phase 2 — In Progress (2–3 weeks)
Demo-Ready — Tasks 8–10 + Deployment
Case intake form (Task 8), Supabase Auth + multi-tenancy + RLS (Task 9), WhatsApp via Twilio (Task 10). Deploy backend to Railway, frontend to Vercel. Live public URL. First client demo possible.
Phase 3 — Months 2–4
Production-Hardened + First Clients
Stripe billing integration, self-serve onboarding wizard, bulk case import (CSV), tenant payment tracking, document storage (correspondence PDFs per case), mobile-responsive UI, rate limiting and API hardening.
Phase 4 — Months 4–12
Market Differentiation
Municipality (gemeente) notification automation — the legally required vroegsignalering step that no competitor automates for the Dutch market. Reporting & analytics dashboard. Tenant payment portal. API for property management software integrations. Enterprise tier for woningcorporaties.
